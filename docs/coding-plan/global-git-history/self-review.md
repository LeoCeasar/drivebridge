# 全局 Git 历史设计自审报告

日期：2026-11-12。模式：单会话自审；没有独立代理复核。对象为设计文档，不是实现代码的完成验收。

## 结论

v1.0 的主要架构可以保留，但并不完整：发现 12 组有实质影响的设计缺口，其中 8 组具有数据完整性、恢复或错误同步风险，另 4 组涉及承诺准确性、支持范围和资源限制。已把处理规则及验收条件补入 v1.1。

上一版 `review_status=passed` 只反映了当时一轮有限自查，不足以支持“全部重要场景已经覆盖”的结论。此次以明确反例修正，不用设计关卡分数或基础 Git 探针代替完整性证据。

修订后的结论：已识别的重要设计缺口已给出处理，可作为后续分块开发的依据；不能保证穷尽所有场景，也不能宣称持久性、性能及三平台行为已经验证。实现前应把本文的反例落到相应模块测试，未通过不得发布相应承诺。

## 本轮实际验证与限制

本轮人工样本探针，macOS Apple Git 2.50.1，结果见 [self-review-probe.json](self-review-probe.json)：

1. 显式 `core.fsync=objects,reference`、`core.fsyncMethod=fsync` 被接受，Git 对象与引用命令成功。
2. 合法空 blob 读出零字节，缺失正文路径返回错误，二者可区分。
3. 一个 blob 的 OID 仅写在 JSON 正文中时，该 blob 不会自动出现在可达对象集合中。

这些结果只核验基础契约。未进行应用归档器、真实磁盘断电、压缩中断、性能或 Windows/Linux 验证；本轮也未重跑与文档改动无关的产品测试。

Git 官方明确：平台默认的对象落盘策略可能在异常关机时丢失近期数据，macOS 的默认 fsyncMethod 也不能直接作为本产品持久归档依据。参见 [Git 持久性配置](https://git-scm.com/docs/git-config#Documentation/git-config.txt-corefsync)；版本读取契约参见 [git-cat-file](https://git-scm.com/docs/git-cat-file)。
