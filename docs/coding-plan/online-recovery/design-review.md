# 在线恢复设计复核记录

日期：2026-11-19。范围为设计，不是代码完成审核。独立审查者：`/root/review_online_recovery_design`，新上下文，只读，无二次分派。作者随后按源码核验并一次修订，未要求重复整份复核。

| 问题 | 依据与重要性 | 核验与处置 |
| --- | --- | --- |
| F01 P1 同账户不能用 profile ID 协调 | `auth/auth.go:833` 的 Link 与 `auth/auth_test.go:341` 允许不同配置/profile 共享 canonical 身份 | 成立。键改为 OS 用户域内已验证 IdentityHash，AuthRef 与 registry 绑定核对；profile 只作为引用/展示 |
| F02 P1 等待记录缺少重启所需字段 | 只有 UTC not_before 无法执行承诺的保守重等；较短/旧事件可能覆盖较长等待 | 成立。增加原始时长、身份、事件版本；更新 CAS 只收紧有效等待；新 worker 本地保守等待不无理由扩大全局冷却 |
| F03 P1 只读核验可能继续云端写入 | `sync/create.go` 回读后可派发改名；`sync/docx.go` 处理未知结果后继续后续操作 | 成立。独立观察接口不暴露 mutation；不调用完整 syncEntry/create/docx。观察证据交正常业务执行器，经正常写入准入与 CAS 消费；recheck 链路需要第二阶段显式调整 |
| F04 P2 会话/暂停解除含义不明确 | dispatcher 每五分钟重入 pending，旧 Paused 可恢复；逻辑核验与多个 CLI 调用不同 | 成立。定义 Bridge 派发、逻辑尝试、有效核验、持久 cycle；重启/轮次/重复点击不重置周期，协议未知暂停只由显式动作或已验证兼容版本变更解除 |
| F05 P2 传输层不知道谁取消 | `lib/larkcli/runner.go` 只有 context 超时/取消事实，无法知道用户意图 | 成立。manager/执行器创建带来源 context；传输仅透传。来源未知不伪造用户取消，不自动放行剩余副作用，允许有界只读观察 |

实施者复核没有发现必须新增正文合并算法才能解决的安全矛盾。用户是否额外扩展正文合并算法仍是独立偏好，不阻塞本文已明确的在线分类和恢复范围。

作者最终自查另外确认：失败分页不生成删除；原父目录缺失只证明离开原同步范围，不证明资源全局删除；长 RetryAfter 不可截短；旧计数不伪造成新有效核验次数；未知错误不能回退为网络；云端结果未知不被细分原因覆盖。

结论：上述五项设计契约均已补齐，设计可进入任务拆分。该结论不代表产品已实现、截图实际根因已确定、线上测试已通过或用户已批准编码。真实账号与平台验收要求保留在设计中。
