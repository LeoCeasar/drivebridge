## 1. 自定义路径安装的 WinFsp 被误判为缺失

- **复现**　在 `D:\Work\WinFsp` 安装驱动。DLL 和服务都存在，DriveBridge 的驱动检查仍可能失败。
- **根因**　Manager 原先只查 Program Files 下的默认位置。Windows 打包和冒烟脚本查的是注册表 64 位视图，而 WinFsp 把安装目录写在 32 位视图（`HKLM\SOFTWARE\WOW6432Node\WinFsp`）。cgofuse 加载 DLL 时读的也是这个视图。
- **处理**　Manager 优先读取 32 位注册表视图中的 `InstallDir`，校验 `bin\winfsp-x64.dll` 存在，保留默认目录回退。两个 PowerShell 脚本改读 `WOW6432Node` 键。
- **复测**　便携包 `feishu doctor --json` 的驱动检查通过，WinFsp 本地真实挂载测试和飞书账号盘挂载通过。完整安装器脚本只做了语法检查。
- **复核意见**　方案合理，与挂载引擎的查找方式一致。限制：只检查 `winfsp-x64.dll`，ARM64 Windows 需要另行处理（应检查 `winfsp-a64.dll`）；当前只发布 x64，暂不影响。

## 2. 首次命令行启动判定状态目录已占用

- **复现**　新用户首次执行 `desktop start`，后台拒绝使用本机状态目录，管理页未启动。
- **根因**　启动器先在未认领的状态目录写 stderr 日志，后台随后拒绝认领这个非空目录。
- **处理**　在创建后台日志之前调用 `InitializeConfig` 认领状态目录。保留首次失败的日志，并把它从状态目录移到测试目录。
- **复测**　重新构建后从未初始化的配置启动，桌面状态为 `running: true`，管理页返回 HTTP 200。
- **复核意见**　方案合理。`desktop _run` 内部还会再调用一次 `InitializeConfig`，这一调用是幂等的，无副作用。

## 3. 中文 Windows 打包阶段读取 UTF-8 输出失败

- **复现**　在本机运行 `package.py stage`，检查 CLI 帮助时触发 GBK 解码错误。
- **根因**　Python 子进程输出按系统默认编码解码，DriveBridge 输出为 UTF-8。
- **处理**　打包脚本的 `run()` 显式按 UTF-8 读取子进程输出。
- **复测**　载荷组装、清单校验、ZIP 生成成功。39 项可在当前 Windows 环境运行的打包测试通过。其余 4 项依赖 Unix shell、Unix 权限位或本机缺少的符号链接权限。
- **复核意见**　对 DriveBridge 自身的输出是对的。但 `run()` 同时用于外部工具；如果 `signtool`、`wix` 等在中文系统按 OEM 代码页输出中文报错，就会反过来触发 UTF-8 解码异常，掩盖真实错误。建议加 `errors='replace'`。

## 4. 授权二维码过期后，管理页再次点授权无可见进展　【r7 已修复并实测】

- **复现**　选择已有 CLI 应用，用户授权二维码失效。关闭旧流程后回管理页点击「授权」，后端立即返回 503。
- **根因**　二维码失效是飞书的授权时限。DriveBridge 把中断的流程保留为待重新核验状态（`auth.ErrNeedsReconcile`），但管理页的自动流程（`internal/bridge/manager/automatic_login.go` 的 `runAutomaticLogin`）调用 `Start`/`StartRecovery` 遇到该错误时直接失败，没有像 CLI `feishu account login`（`cmd/feishu/commands.go`）那样先核验再接续。
- **规避**　从随包 CLI 运行 `feishu account login --profile '账号名称'`。该入口复核已有应用配置并发出新的用户授权链接；授权完成后从管理页打开应用独立登录窗口。
- **复测**　已有应用和账号条目被复用，真实用户授权和 WebView2 登录通过。
- **复核意见**　「问题已解决」不成立：代码未改，用户只能靠命令行规避，普通用户无法自助。修复方向：在 UI 自动流程中捕获 `ErrNeedsReconcile`，复用 CLI 的核验逻辑，并覆盖两种状态：需要重新发起；已有授权其实已经完成。前端要显示可操作的提示，不能只返回 503。

## 5. 重新打开管理页后，旧页仍显示本机会话失效

- **复现**　从浏览器历史打开旧的本机管理页，或在桌面进程重启后继续使用旧标签页。
- **原因**　管理页入口使用短期、一次性的本机引导凭证。旧标签页的会话可能随后台重启失效。
- **处理与复测**　从托盘或 `desktop start` 重新打开管理页。已验证新标签页可用。此项属于会话设计和使用指引。
- **复核意见**　安全设计合理。体验上可以改进：失效页面直接提示「从托盘重新打开」，或提供一键通过本机托盘重新引导的入口。

## 6. WinFsp 已卸载账号盘，安全停止却返回配置错误

- **复现**　队列和在途为零时安全停止。旧路径消失，停止返回 `config`，离线状态也无法查询。
- **根因**　VFS 缓存清单使用 Windows 扩展长度路径（`\\?\D:\...`），归属检查拿它与普通盘符路径直接做 `filepath.Rel` 比较。
- **处理**　比较前用 `file.UNCPath` 把两侧转换成同一种扩展长度形式，保留越界、符号链接和归属检查。
- **复测**　合法长路径和越界拒绝的回归测试通过。实机离线状态可读，同一挂载迁到测试根目录下，并通过修复版安全停止。
- **复核意见**　方案正确。`UNCPath` 在非 Windows 平台是原样返回，不影响其他平台；Windows 上 `filepath.Rel` 比较时不区分大小写。

## 7. 写入时报 I/O 错误，日志显示目录同步被拒绝

- **复现**　在 Windows 账号盘创建合成 TXT，WinFsp 返回 I/O 错误。缓存元数据日志显示目录句柄同步被拒绝。
- **根因**　托管 VFS 在保存元数据、写回正文和恢复已提交的重命名时，会对目录句柄调用 `File.Sync`；Windows 不支持对目录做 `FlushFileBuffers`。
- **处理**　复用项目已有的平台持久化操作：`platform.SyncDir` 和 `platform.ReplaceFile`。文件正文和元数据仍执行文件同步。Windows 上的替换使用 `MoveFileEx(REPLACE_EXISTING | WRITE_THROUGH)`；目录同步在 Windows 上是**空操作**，依靠 NTFS 元数据日志和写穿透的替换保证持久性。
- **复测**　Windows 缓存和重命名恢复相关测试通过。修复后创建文件成功，下一处内容提交故障见第 8 项。
- **复核意见**　方案合理，也是 Windows 上的常规做法。原报告写的「目录同步按平台实现执行」容易让人以为 Windows 上也执行了目录同步，已改为明确说明。

## 8. 写入正文后 Flush 仍报拒绝访问

- **复现**　TXT 可见且有 42 字节，但 `Flush(true)` 失败，后台报告 VFS 待保存，云端没有在途任务。
- **根因**　`overlay.Object.Update` 已用 `PutBlob` 把正文写成按内容寻址的不可变 Blob，并为校验大小打开了该 Blob 的读句柄；接受写入时又走 `Store.Stage`，用同样的正文再执行一次 `PutBlob`，也就是把临时文件改名覆盖同一个 Blob。Go 在 Windows 上打开文件时不带 `FILE_SHARE_DELETE`，因此只要有读句柄，替换就会被拒绝。
- **处理**　新增 `Store.StagePreparedBlob`，在事务内校验 Blob 标识与大小，直接接受已持久化的 Blob；保留代际检查和本地回执规则。`Stage` 也改为复用这一函数。
- **复测**　经用户确认后，先备份并校验唯一的待保存合成文件，再停止卡住的旧 Worker。修复版重新挂载后从原缓存恢复同一份 42 字节 TXT，哈希一致，待保存归零。根目录和子目录 Markdown 写入、Flush 和回读成功。
- **复核意见**　修复正确，但只消除了 `Object.Update` 这一条自身触发的路径。根源在 `PutBlob` 总是覆盖已存在的同名 Blob，其他路径仍会触发同样错误，见第 14 项。

## 9. Windows 测试夹具与挂载路径规则不一致

- **复现**　Manager 回归测试批量返回活动句柄或未确认数据错误，另有符号链接用例因权限失败。
- **根因**　通用夹具提前创建了末级挂载目录，WinFsp 需要该路径留给挂载过程。当前 Windows 用户也没有创建符号链接的权限。
- **处理**　用现有平台挂载路径准备逻辑初始化夹具；需要测试已有本地数据的用例单独准备目录。Manager 的符号链接用例在 Windows 缺少该能力时跳过。
- **复测**　Manager、平台、托盘、飞书命令、原生登录协议和实际 WinFsp 挂载测试通过。Store 的一项符号链接副本用例仍受本机权限限制，Overlay、同步引擎和 VFS 缓存套件通过。
- **复核意见**　合理。跳过的用例应在开启「开发人员模式」（允许创建符号链接）的 Windows 环境或 CI 上补跑，不能计为通过。

## 10. 共享测试目录需要补录

- **现象**　自动扫描完成并发现 9 个可见共享入口，但用户指定的测试子目录本身没有作为一个入口出现。
- **处理与复测**　通过管理页按链接补录。系统核验它属于已有共享根，按原层级展示，最终清单为 10 个去重入口。此项记录发现范围和补录行为，单个子目录未出现在入口清单没有导致挂载失败。
- **复核意见**　符合「三路入口不代表全部子树」的设计。

## 11. 多文件提交的第二份等待时间超过验收窗口　【r7 已修复并实测】

- **复现**　两份真实冲突均复核并选中。首次批处理接受 A 后，B 在 30 秒验收窗口结束时仍显示「正在提交」。
- **原因**　目前只确认延迟发生在提交或复核路径。飞书请求、后台拉取和本地排队各自的耗时还没有分开测量。
- **处理与复测**　重新打开 B，确认草稿仍完整，核对三份来源并单独提交。最终独立挂载读回 A 和 B 的两组标记，账号盘队列、在途和冲突均归零。
- **复核意见**　只是规避，没有找到原因。下一步：用两份新的合成冲突复测，记录 B 的提交请求、重读云端与写回各阶段的时间戳，区分「后端慢」和「前端没有轮询到结果」。

## 12. WiX 4 无法编译 Windows MSI 的文件组件

- **复现**　WiX 4.0.6 编译当前 Windows 安装模板，返回 `WIX0230`。
- **根因**　文件组件使用 HKCU 注册表值作为组件键路径，同时要求 WiX 自动生成组件 GUID，这种组合不满足 WiX 的自动生成规则。
- **处理**　以产品升级码为命名空间、以安装相对路径（不区分大小写）生成 UUIDv5 作为组件 GUID，保持当前用户安装和 HKCU 组件键路径。输出 XML 显式使用 UTF-8 并带 XML 声明。
- **复测**　修复后 WiX 4.0.6 已成功生成未签名 MSI；回归测试确认两次渲染的 GUID 一致。
- **复核意见**　方案合理，跨版本 GUID 稳定，符合 MSI 组件规则。注意：日后改动文件的相对路径会得到新的 GUID，这是正确的组件行为。原生安装、升级和卸载仍需实测。

## 13. 冷占位文件首次打开时句柄长度为 0　【r7 已修复并实测】

- **复现**　账号盘中选一个尚未下载正文的文件（资源管理器显示 0 KB）。示例 `.docx` 实际 15588 字节：在 Windows PowerShell 5.1 中第一次 `[IO.File]::ReadAllBytes` 返回 0 字节，第二次返回 15588 字节。另一个冷原生文档的第一次 `[IO.FileInfo]::new($f).Length` 耗时约 13 秒，返回 0。按流读到 EOF 的 `Copy-Item`、`Get-Content`、`cmd /c type` 首次就能读到完整内容。
- **根因（推断）**　cmount 的 `Getattr` 在托管模式下走 `StatMetadata`，不下载正文，对大小未知的条目报 0；真正的下载发生在 `OpenEx → VFS.OpenFile`。WinFsp 的 FUSE 层在打开文件时，似乎先调用 `getattr`（不带文件句柄）获取文件信息，然后才调用 `open`，并把先前得到的信息返回给内核作为句柄的 FileSize，因此句柄长度停留在 0。macOS 通过 `PurgeAttr` 让内核在打开后重新获取属性，WinFsp 没有对应机制。下载完成后，节点大小已更新，所以第二次打开正常。
- **影响**　凡是按句柄长度分配缓冲或做内存映射的程序，首次打开冷文件都会读到空内容或失败，包括 .NET Framework 的 `ReadAllBytes`、部分编辑器和 Office 类程序。如果用户随后把读到的空内容保存回去，会形成一次真实的空内容写入。
- **建议修复**　仅限 Windows：`Readdir` 为大小未知的条目填写一个占位 stat（避免 WinFsp 对每个条目单独调用 getattr 而导致整目录下载）；不带句柄的 `Getattr` 改走 `VFS.Stat`，即在打开前就完成下载，使 WinFsp 拿到真实大小。需要验证：列目录不触发下载，`GetFileAttributesEx` 和打开得到真实大小，并测量 `FileInfoTimeout`（`attr_timeout`）缓存的影响。
- **规避**　修复前，需要精确字节的脚本先 `Get-Item` 或先读一次，再按长度读取。

## 14. `PutBlob` 覆盖已打开的同名 Blob　【r7 已修复】

- **现象（代码复核）**　`internal/bridge/store/blob.go` 的 `PutBlob` 算出内容哈希后，总是用 `Rename` 把临时文件改名覆盖目标 Blob（注释说明这样可以在早先同步失败后重新保证持久性）。在 Windows 上，只要该 Blob 仍有其他读句柄，改名就会被拒绝。可能的读者包括：正在上传的任务、冲突视图、另一个挂载句柄。
- **触发场景**　保存与正在上传的内容完全相同的正文；两个文件写入相同内容；Flush 重试相同内容。这些情况都会重新执行 `PutBlob`。
- **建议修复**　目标 Blob 已存在且大小一致时（按内容寻址，哈希相同即内容相同），不再改名，只刷新时间戳和目录持久性；或者在 Windows 上把「目标已存在时的共享冲突或拒绝访问」视为成功，先对已有 Blob 做一次哈希校验。修复后，第 8 项的专门处理可以保留作为优化。
- **状态**　尚未在实机上触发，属于代码复核发现，需补一个 Windows 回归测试：持有 Blob 读句柄的同时再次 `PutBlob` 相同内容。

### 实机复测（真实飞书账号，2026-11-12）

- **冷读**（Windows PowerShell 5.1）：冷 Markdown 第一次 `ReadAllBytes` 读到完整 5015 字节（5.6 s），热读 8 ms；第一次 `FileInfo.Length` 和第一次打开的句柄长度都是真实大小；329 KB 的冷 `.docx` 第一次读取即完整，复制件哈希一致。列目录不会下载正文：13 个文件中 6 个冷文件，列目录两次后仍是 6 个，读取 3 个后剩 3 个。
- **批量冲突**：账号盘与独立 X: 挂载同时改同一行，产生两份真实 `overlapping_edits`。一次「提交已选文件（2）」两份都被接受：第一份 5.2 s，第二份 9.0 s，服务端计时显示本地两步各约 20 ms，其余为唯一一次云端复核。约 1 分钟内两边都显示已确认，并互相读回对方提交的合并结果。

### 复测中发现并顺带修复

- **第 15 项**：`auth-view.js` 把原生 `setTimeout`/`clearTimeout` 作为另一个对象的方法调用。Chromium 内核浏览器（包括 Windows 默认的 Edge）会抛出「Illegal invocation」，导致授权进度无法轮询、页面报错。HEAD 上就有这个问题；单元测试注入了假时钟，所以一直没测出来。已改为箭头函数包装，并新增 `auth-native-timers.test.cjs` 回归测试，它在修复前的代码上会失败。

- 状态轮询每次都整体重绘挂载表、合并队列和侧栏列表，导致焦点丢失、点击落空、「更多」菜单被关闭。现在内容不变时不重绘，菜单打开期间也推迟重绘。
- 「待处理」列会在词中间折行，在约 1086 px 宽度时还会把操作按钮挤出面板。现在数字与标签之间用不换行空格，并在 1280 px 以下收紧单元格内边距、取消操作列的最小宽度。
- 已知取舍：Windows 上删除、移动冷文件也会先下载正文；下载失败时该文件暂时不能删除或改名。
