# macOS / Windows 目录发现及时性修复

用户已批准此前完整方案，随后澄清现场只有一台Mac，优先修复macOS/Windows业务逻辑。Linux保持共用代码兼容，不作为本轮原生门禁重点。该文档记录已批准的行为及实现取舍，不重新发起审批。

## 问题与证据

实际云端父目录有12项，本地数据库只有11项；新目录17:21创建，而父目录清单停在16:53。快照显示后台仍连续更新另一分支的深层目录。现有缓存 List 不触发重新查询，1850目录的串行扫描会让正在浏览的父目录等待完整扫描周期。“重试同步”只处理上传工作。

## 方案与边界

采用缓存立即返回、过期目录优先后台刷新的方式；逐次处理优先任务，不等128项批次完成。继续扫描所有目录不解决当前目录时效；让每次文件管理器读取同步等待网络会阻塞文件操作，均不采用。

- 目录缓存超过30秒时，List仅将当前目录加入优先队列，不在文件管理器回调中等待网络。
- 一条有界、去重的优先队列（上限256）；同目录读请求合并，手动请求在已有在途读取之后至多补一次核验。优先任务最多连续处理3项，然后让1项常规扫描推进。
- 现有元数据工作线程消费队列。每个目录读取至多30秒，读完一个目录检查优先任务；空闲时可被新请求唤醒。关闭时停止并排空，不新增游离网络协程。
- 队列捕获目录ID、token与相对路径，执行前重核对；已删除、改名、移出范围或身份变化的旧请求不能刷新其他对象。
- 完整合法分页成功才采用清单。请求失败保留旧条目、本地待上传内容和历史，记录具体原因及持久退避；不能把错误当空目录。服务冷却下限不能因点击缩短。
- 更新成功通过既有 NotifyManagedDirectoryChanged 通知 macOS/Windows VFS；新发现的子目录继续进入元数据扫描，正文仍按需获取。
- 提供定向目录刷新（CLI、受保护的管理页/worker API）。界面显示路径和目录更新时间，缓存覆盖数不当作新鲜度；上传确认与目录刷新状态分别呈现。
- 同一套Go业务逻辑覆盖macOS和Windows；不新增系统权限，不改写云端文件，不清理真实缓存，现场Mac更新须经既有安全安装协调流程，保留数据与历史。

## 验收

真实store与受控只读提供方中复现云端12项、本地11项：过期List立即返回旧清单，优先读取完成后本地为12项，且通知父目录；无需跑完1850项队列。覆盖批次在途插队、反复读取去重、失败保留、上下文期限、停止、分页失败、目录身份漂移、子目录发现、公平性和服务等待。执行macOS本地和Windows原生共享及文件系统门禁；编译与原生执行分别报告。
