# DriveBridge native packaging

These scripts create native packages; native installation and writable mount support remain **not verified** until the corresponding runner produces evidence. They do not install tools/drivers, authenticate accounts, modify system services, sign without explicit keys, or publish releases. Existing `packaging/macos` and `packaging/windows` are legacy launchers; these builders reuse their rclone/CLI/Node licensing requirements, not their account or global-npm discovery. The old macOS NFS fallback is deliberately absent: managed NFS is read-only.

| Native runner | Full build requirements | Outputs | Install location |
|---|---|---|---|
| macOS amd64 / arm64 | macOS 14+, Go, Swift 6, Python 3.9+, Xcode SDK, macFUSE `fuse.h`, pkgbuild, productbuild, hdiutil, codesign | desktop dmg with graphical installer; advanced pkg and portable tar.gz | desktop: `/Applications/DriveBridge.app` or `~/Applications/DriveBridge.app`; advanced pkg: `~/Applications/DriveBridge` |
| Windows x64 | Go, PowerShell 7, Python 3.9+, WiX 4, Inno Setup 6, WinFsp, pinned Node ZIP | msi, installer exe, zip | `%LOCALAPPDATA%\Programs\DriveBridge` |
| Linux amd64 / arm64 | Go, Python 3.9+, dpkg-deb, rpmbuild, tar, FUSE3, `/dev/fuse` | deb, rpm, tar.gz | `/opt/drivebridge`; workers always run as each user |

Build each architecture on its own native runner. Cross-compilation does not pass the architecture gate. Full macOS builds require macFUSE headers; set `DRIVEBRIDGE_FUSE_INCLUDE` only if needed. A missing driver/tool is an error. `--cli-only --unsigned` (Windows `-CliOnly -Unsigned`) explicitly creates test artifacts with `mount:false` and blocks release; the complete installer toolchain is still required. Default builds require signing settings, and full builds verify the compiled `feishu` and platform mount command before staging. No fallback switches to NFS.

## Product editions

Native builders default to the Feishu edition. Unix builders accept `--edition feishu` or `--edition full`; Windows accepts `-Edition feishu` or `-Edition full`. The edition is recorded in the payload manifest and checked against the compiled binary through the offline `feishu edition --json` command. Feishu artifact names include `-feishu`.

The Feishu edition uses the `drivebridge_feishu` Go build tag. It registers only the Feishu/local backends and product, configuration, version and platform mount commands. Authentication, Markdown conversion, synchronization, conflict handling and Git history remain included. The full edition retains the original Rclone commands, backends and plugin registration. A plain `go build` remains a full build; the product tag is opt-in outside the packaging scripts. Edition selection is independent of the writable-mount versus `--cli-only` packaging gate.

Local Apple Silicon version 0.2.6 verification produced a 43.33 MiB Feishu desktop DMG, compared with the previous 88.37 MiB full desktop DMG. The installed application passed mount-removal and cache-cleanup checks; this does not establish Windows/Linux native installation or signing evidence. See [the scoped implementation results](../../docs/coding-plan/global-git-history/mount-cleanup-results.md).

## Optional desktop packages

Add `--desktop` to the native Unix build, or `-Desktop` to the Windows build, to keep the CLI and add a separate desktop entry. The builder requires a read-only `desktop capabilities` response confirming native tray support for the target OS/architecture before staging. The output name gains `-desktop`; manifest `desktop:true` identifies both executables in the exact file inventory. `--desktop --cli-only` / `-Desktop -CliOnly` is rejected: a tray-only test must never masquerade as a full writable client. Default builds package the CLI without a desktop entry; macOS also includes the application-owned login helper.

macOS builds both binaries with native mount support and the desktop binary with `desktop,cmount` and CGO enabled. `DriveBridge.app` has `LSUIElement` and an ICNS icon. Its desktop executable resolves the adjacent payload's `bin/drivebridge` and `libexec/lark/lark-cli`; keep the entire `~/Applications/DriveBridge` directory together. Moving the `.app` alone breaks this deliberate shared runtime layout. The app and CLI are signed before the final manifest is written.

For desktop DMGs, double-click **安装 DriveBridge.app**. This graphical entry defaults to `/Applications/DriveBridge.app`, with the current user's Applications directory available without elevation. The installed outer app contains the complete verified payload in `Contents/Resources/payload`; it can be opened directly from Applications. Login startup and opening the app after installation are visible, checked-by-default options. The installer copies a candidate helper outside the replacement tree, holds the existing maintenance lease throughout a verified staged replacement, and configures startup only after releasing that lease. It never clears user state. An existing known legacy login entry is retired before registering the new executable; unknown entries are retained and reported. Startup/launch failures are reported separately from successful application installation. The app inventory lives in the installer and is refreshed after signing the installed app, before signing the containing installer, avoiding a signature/hash cycle.

The standalone `.pkg` remains an advanced coordinated-installation artifact. Double-clicking it without `upgrade.sh` intentionally fails its preinstall verifier. It is no longer the desktop DMG's visible entry. CLI-only DMGs retain the advanced pkg layout. macFUSE is still required; this packaging repair does not implement the proposed File Provider migration.

Windows adds `bin/drivebridge-desktop.exe` with `-H=windowsgui`, alongside the normal console CLI, plus a current-user desktop shortcut in MSI and Inno. The upstream native Win32 tray supports CGO disabled. WinFsp and all existing native/signing/upgrade gates still apply.

Linux desktop builds require CGO, GTK3 and Ayatana AppIndicator3 development libraries (`pkg-config gtk+-3.0 gio-2.0 ayatana-appindicator3-0.1`). The payload includes an icon, `/opt/drivebridge` application entry for deb/rpm, and `launch-desktop.sh` for a portable directory. Run `sh install-desktop.sh` from an extracted portable bundle to add a current-user application launcher; this does not enable login startup. The desktop environment must expose a supported status notifier tray; a missing GUI/tray is reported explicitly. The existing deb/rpm multi-user lifecycle gate still refuses installation until separately validated.

Launch the `.app`, Windows shortcut or Linux launcher, then use the tray to open the local manager. Explicit CLI control is `bin/drivebridge desktop start`, `status`, `stop`, `enable-autostart` and `disable-autostart` (add `.exe` on Windows). `stop` exits the desktop shell and retains workers; stopping sync is a separate action. Login startup is per OS user: a LaunchAgent in `~/Library/LaunchAgents`, a limited interactive logon task with a user SID in its name on Windows, or an XDG graphical-session autostart entry on Linux. The macOS graphical installer enables it when its default-selected option is kept; portable bundles and other installers require explicit opt-in. macOS/Linux file preferences take effect at the next graphical login and leave the current tray running. Build scripts never register these items. Disable desktop login startup before removing or moving the application directory.

Desktop native evidence additionally requires `desktop_tray`, `desktop_login` and `desktop_upgrade_exit`; macOS also requires the installed-product `native_login` check, bound to the same exact payload hashes. Workflow dispatch defaults the optional desktop switch on; missing native GUI libraries fail the build. Unit tests and cross-compilation do not satisfy these gates. Local Apple Silicon development validation has built a full `desktop,cmount` package and completed a current-user native pkg installation through Installer.app. Signing, tray visibility, native login startup, writable mounting and pending-data upgrade validation are separate gates; see `docs/manual/验证记录.json` for the actual run. Windows/Linux native installation and login are not verified here.

## Application-owned native login

macOS packages require macOS 14 or later and include `libexec/DriveBridge Session.app/Contents/MacOS/drivebridge-session-host`. The builder compiles `native/session-host/main.swift` with Swift 6 for `arm64-apple-macos14.0` or `x86_64-apple-macos14.0`, linking system Cocoa and WebKit. The helper is an accessory app (`LSUIElement=true`, no separate Dock tile) with bundle ID `org.drivebridge.sessionhost`, executable `drivebridge-session-host`, and `LSMinimumSystemVersion:14.0`. This ID deliberately matches the verified compatibility prototype so the intended per-account WebKit storage identity remains stable. The main desktop app and Installer distribution also declare the minimum macOS version. Native session compatibility still requires actual installed-product validation.

For portable inputs, macOS `package.py stage` requires `--session-host-binary /absolute/built/helper`; other platforms omit it. Staging generates the helper app Info.plist, checks its fixed identity, activation mode and minimum OS, and inventories both the executable and plist. macOS signing signs the helper app before writing the final manifest; release smoke verifies that signature. The manifest records `native_login` availability/provider/minimum OS and keeps native verification `not_verified`. A hash-bound `native_login` evidence check is required for macOS native release verification; prototype observations alone do not satisfy it.

Windows/Linux Go sources remain compilable and their existing CLI/sync payloads are retained. Their application-owned login provider is currently unavailable: neither a missing Swift helper nor a browser extension is required by those packages. WebView2 and WebKitGTK are possible later platform work, not shipped or validated providers.

Login runs in the app-owned WKWebView window. Personal Chrome/Edge/Safari profiles and browser extensions are not dependencies. Per-user, per-product-account website data is stored outside the application payload by WebKit; the package contains no Cookie, account state or session store. Closing the login window hides it while directory requests remain available; session expiry asks the user to reopen login. The window is for login and directory discovery, not a compatibility claim for the whole cloud-drive website. File bodies and writeback still use the official CLI.

The prototype validated current-account login, 12 deduplicated folder entrances, hidden-window reads, helper/control-process restart reuse, and a fresh isolated store. Formal Manager integration, installed app login/restart/isolation and account-disk checks must be recorded separately in [owned-login-verification.md](../../docs/coding-plan/feishu-desktop-client/owned-login-verification.md). No signed/notarized release or Windows/Linux native-login result is claimed here.

## Pinned public runtime inputs

`runtime-lock.json` pins CLI 1.0.99 to the [official npm metadata](https://registry.npmjs.org/@larksuite/cli/1.0.99), its SHA-512 tarball integrity, individual package file hashes, and all five native release asset SHA-256 values from that package's `checksums.txt`. The native archives come from [Lark's official release](https://github.com/larksuite/cli/releases/tag/v1.0.99). Windows Node 24.22.2 is a packaging input selected from the [official distribution index](https://nodejs.org/dist/index.json), pinned to the [official SHASUMS256 file](https://nodejs.org/dist/v24.22.2/SHASUMS256.txt) for both ZIP and executable. These pins do not establish Windows runtime compatibility; native validation is still required. Every native executable was also read with `go version -m` without execution: module `github.com/larksuite/cli v1.0.99`, VCS commit `8d8357d39dd15ac5e9aa815d4ab2639d56bd3239`, `vcs.modified=false`, and expected OS/architecture. This actual artifact source commit is distinct from any later inspected source-checkout HEAD. Runtime updates must update checksums and repeat native evidence.

`fetch-runtime.py` downloads only those public inputs, verifies hashes, and extracts named regular package files. It does not execute npm hooks, install globally, or inspect an existing account. Alternatively supply those exact files from an offline cache. Builders verify the package files and native archive again before copying. An arbitrary globally installed CLI or Node executable is insufficient.

```sh
python3 packaging/drivebridge/fetch-runtime.py --platform darwin --arch arm64 --output /tmp/db-runtime
bash packaging/drivebridge/build-macos.sh --arch arm64 --version 0.1.0 --unsigned \
  --lark-package /tmp/db-runtime/lark-package \
  --lark-native-archive /tmp/db-runtime/cli-native.tar.gz
# On Linux use --platform linux above and build-linux.sh, on the native architecture.
```

```powershell
python packaging/drivebridge/fetch-runtime.py --platform windows --arch amd64 --output "$env:TEMP/db-runtime"
pwsh -File packaging/drivebridge/build-windows.ps1 -Arch amd64 -Version 0.1.0 -Unsigned `
  -LarkPackage "$env:TEMP/db-runtime/lark-package" `
  -LarkNativeArchive "$env:TEMP/db-runtime/cli-native.zip" -NodeArchive "$env:TEMP/db-runtime/node.zip"
```

Output defaults to `dist/drivebridge-VERSION-PLATFORM-ARCH[-unsigned-test]/`. Existing output is never removed. The build uses a private temporary staging directory, `go build -trimpath`, then publishes the artifact directory only after all native packaging/signing commands succeed. Go dependencies must be provisioned or accessible through the normal Go toolchain. No private validation runtime is copied.

Payload layout is fixed: `bin/drivebridge[.exe]`, `libexec/lark/lark-cli[.exe]`, `licenses/`, `README.md`, and `manifest.json`. macOS additionally carries `libexec/DriveBridge Session.app/`; browser extensions and Native Messaging hosts are not distributed. Windows additionally carries `libexec/node/node.exe` and the verified official package at `libexec/lark/package/` (`scripts/run.js` is its actual launcher). The managed runner resolves the native CLI from the application installation directory, never a hardcoded developer path. Node is retained for package compatibility; workers invoke the native CLI directly. The official CLI's own self-update changes its hash and therefore requires renewed capability validation; it is not silently trusted by the application.

The payload is an allowlist. Unexpected config/account files, symlinks, startup entries, missing licenses, and embedded absolute user-home/developer paths fail the build. The byte-verified official CLI embeds upstream `/home/runner/go/pkg/mod/` and `/home/runner/work/` Go source paths plus literal `/Users/.../` and `/home/.../` documentation placeholders. Only those exact prefixes are allowed in the checksum-verified vendor executable roles, recorded in `vendor_metadata`; our executable and all text still reject real developer paths. Our binary also contains exact public upstream help samples from `cmd/mountlib/rc.go`, `fs/config/rc.go`, `vfs/rc.go`, `backend/sftp/sftp.go`, and `cmd/bisync/rc.md`; only the seven full path literals recorded in `product_help_examples`, with token boundaries, are allowed. They do not allow source-directory prefixes. Vendor executables are not rewritten to conceal this upstream metadata. `manifest.schema.json` describes relative paths, per-file SHA-256 and size, Go/CLI/Node/install-tool versions, architecture, mount engine and signing status. `artifacts.json` records container hashes and the exact manifest hash without recursive self-hashing. The embedded manifest always says native verification is outstanding: evidence is a separate hash-bound result produced after installation. A `signed` manifest alone is never a release assertion.

## Installer and lifecycle boundaries

The advanced macOS pkg Distribution enables only `currentUserHome`; its relative `Applications/DriveBridge` payload stays separate from `Library/Application Support/DriveBridge` state. The graphical desktop DMG installs a self-contained app as described above. Windows MSI uses `Scope=perUser`; Inno uses `PrivilegesRequired=lowest`. Linux package management writes `/opt` through the normal package manager, but installs no root service. Raw native package scripts do not run workers, enable login startup or write credentials. The CLI owns the one startup definition: `feishu mount enable-autostart NAME` / `disable-autostart NAME` uses launchd user agents, systemd --user, or an interactive user task. No worker runs as SYSTEM. Desktop mode owns one desktop login definition and coordinates legacy per-mount startup; the graphical Mac installer uses that definition when its startup option is selected.

The concrete manager `WithInstallationLease` holds the same-user global auth lifecycle exclusion, sorted configuration locks, historical runtime locks and actual Store writer locks through the synchronous installer child's completion. It authenticates historical worker endpoints across config hashes and requests preserve-pending stop; all handles must close, and unaccepted dirty/corrupt cache or a missing/wrong Store root refuses replacement. Valid queued/unknown/conflict bytes remain unchanged. The lease itself makes no cloud/auth request; a previously running worker may finish its existing synchronization before it stops. Cancellation during child execution does not release ownership before child exit.

Run `upgrade.sh /absolute/candidate/bin/drivebridge -- /absolute/synchronous-installer [args...]` (PowerShell 7+: `upgrade.ps1 -Candidate C:\candidate\bin\drivebridge.exe -Installer C:\Windows\System32\msiexec.exe -InstallerArguments @('/i','C:\candidate\drivebridge.msi','/qn')`) as the current desktop user. The candidate helper is copied outside the replacement tree. It creates a random, live loopback proof only inside the lease callback and publishes its descriptor in the canonical OS account home at `.drivebridge-install/lease.json`, with private permissions. The descriptor only locates the authenticated live endpoint; it is removed on exit and does not act as an editable success marker. The bearer is excluded from the child environment because native Installer services can log inherited environment variables. The native package runs its own embedded trusted verifier, never an environment-selected executable. The verifier does not create a Manager or acquire locks. Proof expires when the child exits; wrong identity, stale endpoint, unsafe descriptor path and missing proof fail closed. The verifier can discover the descriptor even when Installer strips the environment. This is coordination between cooperative same-user product processes, not an anti-tampering boundary against that user replacing their executables or forging a localhost service. Arbitrary detached installers are unsupported. On macOS, `/usr/bin/open -n -W -a /System/Library/CoreServices/Installer.app /absolute/candidate.pkg` is the native GUI test invocation: `-n` creates an owned Installer instance and `-W` retains the lease until that application exits. Closing the installer must actually end the owned instance before the lease is released.

The pkg script embeds the signed candidate in Scripts; MSI uses an immediate impersonated [BinaryRef executable action](https://docs.firegiant.com/wix/schema/wxs/customaction/); Inno extracts its [dontcopy/noencryption resource](https://jrsoftware.org/ishelp/topic_isxfunc_extracttemporaryfiles.htm). All three require proof even on fresh install to avoid unsafe existence-check bypasses. Current-user macOS pkg installation with stripped environment has passed a local development run. Other native installer identities/lifetimes, signing and upgrades with queued data remain **not verified**. Builders emit `upgrade_guard:lifecycle_lease_unverified`; release verification rejects it regardless of evidence placeholders. Linux root/system package replacement affects multiple users, so deb/rpm scripts explicitly refuse install/upgrade/removal pending multi-user coordination. Inno uninstall similarly refuses until its separate trusted verifier lifetime is implemented. MSI prevents downgrade; Inno checks recorded version. No installer removes user data or starts SYSTEM workers. Do not mix MSI and Inno installations.

Uninstall through MSI/Inno/deb/rpm removes only tracked application files; user configuration, credentials, blobs and caches are outside those paths. macOS has no automatic uninstaller: stop mounts and disable their startup items, then remove **only** the installed application (`/Applications/DriveBridge.app` or `~/Applications/DriveBridge.app` for the graphical installer; `~/Applications/DriveBridge` for the advanced pkg). Portable removal has the same stop/disable requirement. There is no “clear user data” installer action.

## Signing and release gates

Omit `--unsigned` only on a provisioned signing runner:

- macOS: `DRIVEBRIDGE_CODESIGN_IDENTITY` (Developer ID Application), `DRIVEBRIDGE_INSTALLER_IDENTITY` (Developer ID Installer), `DRIVEBRIDGE_NOTARY_PROFILE` (preprovisioned notarytool keychain profile). The script first verifies the official archive **and unpacked native hash**, then signs that exact CLI with hardened runtime/timestamp. It calculates the post-sign hash, compiles our app with manager `ReleaseCLIArtifactSHA256` and `ReleaseCLIUpstreamSHA256` via `-X`, and only then signs our app. Runtime requires the compiled upstream hash to match the fixed official OS/arch map; there is no editable manifest/config capability grant or normalization of an unknown binary. The optional manifest `cli_binding` field records provenance only. Unsigned builds keep raw vendor bytes unchanged. pkg and dmg are notarized and stapled. The tar carries the same signed executable bytes as the notarized pkg; it has no staple-able tar container.
- Windows: `DRIVEBRIDGE_SIGN_CERT_SHA1`, `DRIVEBRIDGE_TIMESTAMP_URL`, and signtool. Our binary, MSI, setup EXE and Inno uninstaller are signed. Vendor binary signatures are preserved. ZIP contains the signed payload.
- Linux: `DRIVEBRIDGE_GPG_KEY`, gpg, dpkg-sig and rpmsign. deb/rpm receive package signatures and all three containers get detached signatures. Trust roots/public keys must be provisioned independently for verification.

Missing signing secrets fail; only explicit unsigned test builds are allowed. Scripts do not import/export credentials. No publishing action is included.

`smoke.sh` / `smoke.ps1` require payload, artifact directory, an explicitly supplied disposable real mounted filesystem, and native evidence. They verify hashes, native OS/arch, driver, commands, write/fsync/read/rename on that mount, and release signatures when requested. The mount probe deletes only its own newly created directory. It does **not** inject disk errors or install/uninstall by itself. Those actions, stop feedback, startup and upgrade retention must be proven by the provisioned native harness; absent evidence fails instead of returning a successful skip. T13 adds deeper end-to-end fixtures.

The runner-owned harness receives `--artifacts DIRECTORY --result FILE`. It must perform installation, user startup, pending/conflict upgrade retention, stop, uninstall retention, driver and error feedback tests, then leave a disposable mount and installed payload. Result JSON contains absolute local `payload`, `mountpoint`, `evidence` paths. Evidence JSON has this structure (all checks must be `passed`, not copied from an example):

```json
{
  "platform": "linux", "architecture": "amd64", "runner": "native-runner-identifier",
  "payload_sha256": "SHA256 of canonical sorted-key compact JSON manifest.files",
  "checks": {
    "driver": "passed", "install": "passed", "mount_read_write_rename": "passed",
    "flush_error_feedback": "passed", "stop": "passed", "upgrade_preserves_pending": "passed",
    "uninstall_preserves_userdata": "passed", "user_startup": "passed"
  }
}
```

Use `package.payload_digest(manifest['files'])` to derive the binding. Retain the actual runner logs with the evidence; the evidence is an attestation input from that controlled runner, not a substitute for running tests.

The workflow's native matrix uses five provisioned self-hosted runners labelled `drivebridge-native` plus OS/CPU. `NATIVE_HARNESS` is a protected environment variable path. Signing keys live only in protected platform environments. Native jobs only run on manually selected default branch/protected release tags, never PR code. A missing runner remains unverified/queued; missing driver, harness, evidence, key or failed check blocks that platform and the final release gate. An unsigned artifact is always named `unsigned-test`. Unit jobs reference only existing packages. The workflow does not publish or imply that an unavailable platform passed.
